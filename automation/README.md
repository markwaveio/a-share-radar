# 自动化设计

## 设计目标

每个交易日无人工干预，在两个固定时点生成四张 Excel 表，并且**出错时能被发现**。

最后半句是重点。一个每天安静跑着但某天开始产出错误数据的系统，
比一个明确报错停掉的系统危险得多。

## 调度设计

| 批次 | 时间 | 任务 | 缓冲理由 |
|---|---|---|---|
| midday | 11:40 | 需求 1 | 11:30 午盘收盘 + 10 分钟等数据落库 |
| close | 15:15 | 需求 1、2、3、4 | 15:00 收盘 + 15 分钟等资金流数据 |

**为什么午盘不跑需求 2、3、4**：

- 需求 2 的成交量要整个交易日才完整，半天的量没有可比性
- 需求 4 的资金流数据东财在盘中不更新历史序列
- 需求 3 的资讯量是 48 小时滚动窗口，一天跑一次够了

## 交易日闸门

不维护本地节假日表 —— 那东西每年要人工更新，忘了更新会**静默跑错**。

改成问数据本身：拉上证指数最新日线，看日期是不是今天。
交易所调休也能自动跟上。

```python
# radar/trading_calendar.py
def is_trading_day() -> Optional[bool]:
    if today.weekday() >= 5: return False      # 周末直接判掉，省一次请求
    return latest_index_date() == today
```

**判断不了时（网络故障）返回 None，脚本按交易日继续跑。**
宁可在非交易日多生成一份重复报表，也不要在交易日因为网络抖动漏掉一次。

## 可靠性设计

抓 3.3 万次请求，任何一个环节的失败率放大后都会变成整轮失败。三道防线：

| 防线 | 机制 | 位置 |
|---|---|---|
| 限流 | 令牌桶，默认 30 QPS 全局共享 | `radar/http.py` TokenBucket |
| 重试 | 指数退避 3 次 + 随机抖动 | `radar/http.py` get_json |
| 缓存 | 磁盘缓存 30 分钟，崩溃后重跑可复用 | `radar/http.py` _cache_path |

第四道是**统计**：每轮结束汇总成功/失败数，写进日志和 Excel 的口径说明页。
失败率是这套系统唯一的健康指标。

## 内存设计

按股票并发，不按周期并发：

```text
每个线程 -> 一只股票 -> 拉 6 个周期 -> 立刻算指标 -> 丢掉原始 DataFrame
```

如果先把 5500 × 6 × 120 根 K 线全读进内存再算，内存会撑不住。

## 失败时往哪边倒

自动化系统里到处是这类决策，全部显式写在代码注释里：

| 场景 | 选择 | 理由 |
|---|---|---|
| 交易日判断不了 | 当作交易日，继续跑 | 漏跑的代价 > 多跑一次 |
| 某只股票抓失败 | 跳过，计入失败数 | 单只失败不该拖垮整轮 |
| 某个周期没数据 | 该列留空 | 留空 ≠ 0，见 indicators.py |
| K 线数量不足 | 不给数 | 小样本失真比缺数更危险 |
| 开机时错过了批次 | 不补跑 | 补跑会用今天的数覆盖出错误时点的快照 |

## 数据保留

| 内容 | 保留 | 清理方式 |
|---|---|---|
| Excel 报表 | 60 天 | `run_radar.sh` 里 `find -mtime +60 -delete` |
| 运行日志 | 30 天 | 同上 |
| 请求缓存 | 30 分钟 TTL | `cache_ttl_seconds` |

要长期留档做回溯，另存到别的目录，或改脚本里的天数。

## 明确不做的事

- **不接交易接口。** 这是项目边界，不是技术限制。
- **不做实时推送。** 两个固定批次已经覆盖需求，实时推送会诱导盯盘。
- **不做涨跌预测。** 所有指标都是对已发生事实的统计描述。
- **不把频率调到远超正常使用。** 既是稳定性问题，也是分寸问题。
