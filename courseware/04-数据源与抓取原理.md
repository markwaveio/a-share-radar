# 04 数据源与抓取原理

## 这一讲要打开的黑盒

学员平时在行情 App 上看 K 线。App 的数据从哪来？
答案是一批公开的 HTTP 接口 —— 我们用的和 App 用的是同一套。

演示：

```bash
curl 'https://ifzq.gtimg.cn/appstock/app/fqkline/get?param=sh600000,day,,,5,qfq'
```

屏幕上出现浦发银行最近 5 天的前复权 K 线：

```json
{"code":0,"data":{"sh600000":{"qfqday":[
  ["2026-08-07","9.260","9.210","9.290","9.140","565457.000"], ...
```

**这就是整个项目的地基。** 一个 URL，一行命令，全市场的行情数据。

## 第二个演示：让学员看到"接口是会挂的"

紧接着跑这一条（东方财富的 K 线接口）：

```bash
curl 'https://push2his.eastmoney.com/api/qt/stock/kline/get?secid=1.600000&klt=101&fqt=1&lmt=5&fields1=f1,f2&fields2=f51,f52,f53,f54,f55,f56'
```

在写这份课件时它返回：

```text
curl: (52) Empty reply from server
```

**这不是网络故障。** TCP 和 TLS 握手都成功了，服务端接受连接后直接关闭、一个字节都不回。
同一时刻同一台机器上，东财的其他接口（股票池、资讯检索）完全正常。

这个演示比任何理论都有说服力：**第三方接口没有服务承诺，它会在你毫无准备的时候挂掉。**
整个项目的多数据源设计就是为了这一刻。

> 讲课提示：如果演示时东财恰好恢复了，把这段当作"曾经发生过"来讲即可 ——
> 接口时通时断本身就是要传达的事实。反过来如果腾讯那条也挂了，
> 就现场跑 `python3 run.py --task 1 --limit 5` 看它自动降级到哪个源，效果更好。

## 更隐蔽的失败：HTTP 200 但没有数据

再跑一条（东财的延时行情主机）：

```bash
curl 'https://push2delay.eastmoney.com/api/qt/stock/kline/get?secid=1.600000&klt=101&fqt=1&lmt=5&fields1=f1,f2&fields2=f51,f52,f53,f54,f55,f56'
```

它返回 **HTTP 200**，JSON 格式完全合法 —— 但里面没有 K 线。

而且**它的"没有数据"还不止一种长相**。这两种形态在两天内都真实出现过：

```text
形态 A（开发时）:  {"rc":0,  ..., "data":{"code":"600000","klines":[]}}
                        └ rc=0 表示成功        └ 但 klines 是空数组

形态 B（现在）:    {"rc":102,..., "data":null}
                        └ rc 变成 102           └ data 直接是 null
```

**这比直接失败危险得多。** 只检查 HTTP 状态码的代码会认为一切正常，
然后把空数据一路传下去，最后 Excel 里那一列全是空白，日志里一条错误都没有。

而且注意：只检查 `rc == 0` 也挡不住形态 A。

课堂要点：

```text
接口"可用"有四个层次：
    能连上 → 返回 200 → 业务码正常 → 真的有你要的数据

只验证前三层的代码，会在第四层安静地失败。
唯一可靠的判据是：把你真正要用的那个字段取出来，看它是不是空的。
```

`radar/providers.py` 里就是这么写的：业务码只用来快速短路，
**最终判据始终是"目标字段取出来非空"**，取不到就返回 `None` 交给下一个源。

还有个细节值得讲：代码里写的是 `(payload.get("data") or {}).get("klines")`。
那个 `or {}` 就是为了吃掉形态 B 的 `data: null` ——
不写的话会抛 `AttributeError: 'NoneType' object has no attribute 'get'`，
整只股票直接失败，而不是优雅降级到下一个源。

## 两套参数体系

不同数据源的参数长得完全不一样，但表达的是同三件事：**哪只股票、什么周期、复权方式**。

### 腾讯（当前主源）

```text
param = sh600000 , day , , , 120 , qfq
         └股票     └周期      └根数  └复权
```

| 周期写法 | 含义 | | 复权写法 | 含义 |
|---|---|---|---|---|
| `day` / `week` / `month` | 日/周/月 | | `qfq` | 前复权 |
| `m60` / `m30` / `m15` | 分钟（走 mkline 路径） | | `hfq` | 后复权 |
| | | | 留空 | 不复权 |

股票代码前缀：`sh` = 上海，`sz` = 深圳。

### 东方财富（备源）

**`secid` = 市场.代码**

```text
1.600000  上海（市场号 1）
0.000001  深圳（市场号 0）
90.BK0465 板块（市场号 90）
```

**`klt` = K 线周期**

| klt | 周期 | klt | 周期 |
|---|---|---|---|
| 15 | 15 分钟 | 101 | 日线 |
| 30 | 30 分钟 | 102 | 周线 |
| 60 | 60 分钟 | 103 | 月线 |

**`fqt` = 复权方式**：0 不复权 / **1 前复权** / 2 后复权。

### 两个共同点

**1. 都没有 120 分钟。** 需求里要，所以自己用 60 分钟合成 —— 见第 05 讲。

**2. 算技术指标必须前复权。** 除权那天股价会跳空（比如 10 元变 5 元），
不复权的话 KDJ 会算出一个巨大的假死叉。这是新手最容易踩的坑，课上要举实例。

`radar/providers.py` 里 `secid_to_symbol()` 就负责这两套体系的转换：
`1.600000` → `sh600000`。

## 返回值怎么解析

两个源的 K 线都是**数组里套数组**，而且——这是个巧合但很省事——**字段顺序完全一致**：

```text
腾讯:  ["2026-08-07", "9.260", "9.210", "9.290", "9.140", "565457.000"]
东财:  "2026-08-07,9.260,9.210,9.290,9.140,565457"   （逗号分隔的字符串）
        日期        开盘    收盘    最高    最低    成交量
```

注意顺序是 **开、收、高、低**，不是常见的 OHLC（开、高、低、收）。
写代码时把顺序搞错，KDJ 会算出看起来"差不多但就是不对"的值 —— 最难查的一类 bug。

**但单位不一定一致。** 腾讯和东财的成交量单位是「手」，新浪是「股」，差 100 倍。
`radar/providers.py` 里统一折算成「手」再往下传：

```text
所有 provider 必须返回同一套 schema，否则下游指标层要为每个源写一遍。
```

这条是多数据源设计的核心纪律 —— 差异必须在数据层消化掉，不能漏到业务层。

## 5500 只股票怎么在几分钟内抓完

单只股票要 6 个周期，全市场就是 **5500 × 6 ≈ 3.3 万次请求**。
串行按每次 200ms 算要 110 分钟，必须并发。三个工程问题：

| 问题 | 解法 | 代码位置 |
|---|---|---|
| 请求太快被封 IP | 令牌桶限流（默认 30 QPS） | `radar/http.py` TokenBucket |
| 网络抖动导致整轮失败 | 指数退避重试 3 次 | `radar/http.py` get_json |
| 跑到一半崩了要重头来 | 磁盘缓存，30 分钟内复用 | `radar/http.py` _cache_path |

并发数在 `radar/config.py` 的 `concurrency`，默认 12。
调高不一定更快 —— 被限流后重试反而更慢。课上可以让学员试 `--concurrency 4` 和 `--concurrency 24` 各跑一次 `--limit 100`，对比耗时。

## 为什么按股票并发，不按周期并发

```python
# radar/scan.py
每个线程负责一只股票 -> 拉完它的 6 个周期 -> 立刻算出指标 -> 丢掉原始数据
```

如果先把 5500 只 × 6 周期 × 120 根 K 线全部读进内存再算，内存会撑不住。
"抓一只、算一只、扔一只"是这类批量任务的标准做法。

## 多数据源与自动降级

开头那两个演示已经说明了问题：**单一数据源是这类系统最大的单点故障。**

`radar/providers.py` 的做法是给每个周期配一条优先级链，前一个拿不到就试下一个：

```text
月/周/日     东财 → 腾讯 fqkline → 新浪
60/30/15    东财 → 腾讯 mkline  → 新浪
120 分钟     由 60 分钟合成
```

三个设计决定值得讲：

**1. 东财排第一，即使它现在挂着。**
这样它恢复后**无需改任何代码自动切回**。每轮结束打印命中统计
（`数据源命中：tencent 900次(50%) tencent_min 900次(50%)`），
用来发现"东财悄悄恢复了"。

**2. 优先级不是按"哪个好"排，是按实测的承载能力排。**
实测：全市场 5200 只的压力下，**新浪 28 秒就被限流打死**（之后 20 次串行请求全失败），
腾讯 20 次串行 0 失败。所以腾讯做主源，新浪降为兜底。
这个结论只能压测出来，不能靠猜。

**3. 熔断器必须可恢复。**

没有熔断器，一个挂掉的源会让整轮跑不完 —— 每次请求 3 次重试 + 退避 ≈ 2~4 秒，
3.1 万次无效等待 ≈ 20 小时。

但**永久熔断也是错的**：

```text
被限流的源 ≠ 死掉的源。
区分这两者的唯一办法，就是过一会儿再试一次。
```

所以是半开状态：连续失败 8 次 → 熔断 → 冷却 90 秒 → 放**一个**探针 → 成功就完全恢复。
只统计**连续**失败，一次成功就清零，避免把偶发抖动误判成宕机。

课堂演示：跑 `python3 run.py --task 1 --limit 30`，日志里会看到

```text
数据源 eastmoney 连续失败 8 次，熔断 90.0 秒后重试
数据源命中：tencent 90次(50%)  tencent_min 90次(50%)
```

90 + 90 = 180 = 30 只 × 6 周期。**命中数对不上就是有周期在静默缺失** ——
这是每次改数据源之后必查的一个数。

## 使用第三方接口的纪律

- 这些接口**没有官方文档，也没有服务承诺**。字段可能改名，接口可能下线。
- 所以代码里每一次请求失败都要计数，最后汇总到日志（`失败 N 只`）。
- 失败率突然从 0.1% 涨到 30%，就是接口变了或者被限流了，要人工看。
- **不要把频率调到远超正常使用**。这既是稳定性问题，也是基本的分寸。
