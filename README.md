# A股行情雷达（A-Share Radar）

把 A 股全市场的盯盘筛选动作，从每天两小时的人工翻页，变成每个交易日自动生成的四张 Excel。

**它不预测涨跌。** 产出是候选池，不是买卖信号。

```
每交易日 11:40 / 15:15  →  自动抓取全市场数据  →  四张 Excel  →  你只需要读表
```

| 需求 | 输出 | 内容 |
|---|---|---|
| 1 | `01_KDJ全周期_*.xlsx` | 全市场 × 10 个周期的 KDJ（月/周/日/120/60/30/15分钟） |
| 2 | `02_成交量异动_*.xlsx` | 变异系数 CV + 放量倍数 + 放量 TOP200 |
| 3 | `03_咨询量变化_*.xlsx` | 48 小时资讯量 vs 前两周日均 + 升温 TOP100 |
| 4 | `04_板块热度_*.xlsx` | 板块主力净流入占全市场比例，4 个交易日趋势 |

---

## 一分钟上手

```bash
gh auth login && gh repo clone markwaveio/a-share-radar    # 仓库是 private
cd a-share-radar

./install.sh          # 一键：装依赖 → 自检 → 抓 30 只验证 → 装定时任务
```

`install.sh` 七步渐进，任何一步失败都会停下说清原因。依赖它自己处理
（Homebrew Python 3.12+ 被 PEP 668 挡住时会自动建 `.venv`，无需手动 activate）。

装完之后：

```bash
python3 run.py --task all      # 跑全部四个需求，全市场约 20 分钟
```

也可以让 Agent 引导安装（见 [SKILL.md](SKILL.md)）：在 Claude Code 里说
「安装 A股行情雷达」。它比脚本多做三件事——带你**对照行情软件验证 KDJ 准确性**、
解释日志里的每个异常、带你读第一份报表。

完整的安装方式（含 SSH 和离线包）见 [INSTALL.md](INSTALL.md)。

# 运作原理

## 整体是一条单向流水线

没有常驻进程，没有数据库，没有服务端。**每次运行都是一个跑完就退出的进程。**

这是刻意的：常驻服务出问题时会安静地跑错，一次性进程要么出文件要么不出，状态只有两种。

```
launchd 定时  →  shell 批次脚本  →  Python 主程序  →  Excel 文件
  (系统)         (交易日闸门)        (抓取+计算)       (data/output/)
```

**整个链路 0 token 消耗** —— 纯 Python + HTTP，不经过任何模型。

## 四层结构

### 第 1 层：触发（`scripts/run_radar.sh`）

launchd 在 11:40 和 15:15 各调一次，传参 `midday` 或 `close`。

```
midday（11:40）→ 只跑需求 1     成交量/资金流要等收盘才完整
close （15:15）→ 四个需求全跑   收盘 + 15 分钟缓冲，等资金流数据落库
```

**缓冲时间不是随便定的。** 15:00 整点去拉资金流，经常拿到的还是 14:xx 的数据。
自动化任务的时间点必须匹配**数据的可用时刻**，不是交易的结束时刻。

**交易日闸门**：不维护本地节假日表（每年要人工更新，忘了会静默跑错），
改成拉上证指数最新日线看日期是不是今天。交易所调休也自动跟上。

判断不了时（网络故障）**按交易日处理继续跑** —— 宁可在非交易日多生成一份重复报表，
也不要在交易日因为网络抖动漏掉一次。

### 第 2 层：抓取（`radar/scan.py` + `radar/providers.py`）

全市场约 5200 只，每只 6 个周期 = **3.1 万次请求**。三个工程问题：

| 问题 | 解法 | 位置 |
|---|---|---|
| 请求太快被封 | 令牌桶限流（默认 30 QPS，全局共享） | `radar/http.py` |
| 网络抖动整轮失败 | 指数退避重试 3 次 | `radar/http.py` |
| 跑到一半崩了 | 磁盘缓存 30 分钟，重跑可复用 | `radar/http.py` |

**按股票并发，不按周期并发**：

```
线程 1 → 600000 → 拉 6 个周期 → 立刻算指标 → 丢掉原始数据 → 返回 2 行
线程 2 → 600004 → 同上
...   默认 12 个线程并行
```

反过来（先把 5200 × 6 × 120 根 K 线全读进内存再算）内存会撑不住。
抓一只、算一只、扔一只。

### 第 3 层：计算（`radar/indicators.py`）

纯函数，输入 DataFrame 输出数值，不碰网络不碰文件 —— 所以能离线单元测试。

需求 1 和需求 2 **共用同一次抓取**：日线拉一次，KDJ 用它算「上一日/本日」，
成交量 CV 也用它算。省掉一半请求。

120 分钟是**算出来的**，不是拉来的 —— 没有数据源提供这个周期，
用 60 分钟线每 2 根合成（A股每天 4 根 60 分钟 → 2 根 120 分钟）。

### 第 4 层：输出（`radar/excel.py`）

需求 1 是两行合并表头：第一行周期（跨 3 列合并），第二行 K值/D值/J值，共 **32 列 / 12 个合并区**。

每个 xlsx 都带一个「口径说明」sheet，写清参数、数据源、空值含义、本次失败数。
**因为 Excel 会被转发，文档不会跟着走。**

## 多数据源与自动降级

单一数据源是这类系统最大的单点故障。实测过的故障形态：

- 东财对某些出口 IP 的**批量/历史类**接口返回「Empty reply from server」
  （TCP+TLS 握手成功，服务端直接关连接），而同一时刻单只实时类接口完全正常
- 封锁粒度是**按路径**的：同一台主机上 `kline` 死了、`fflow` 活着
- 腾讯 `web.ifzq` 子域在稍高频率下会触发 WAF（返回 HTML 跳转页而非 JSON）
- 新浪扛不住全市场负载，28 秒就被限流打死

所以 `radar/providers.py` 做了优先级链 + 自动降级：

| 周期 | 优先级 |
|---|---|
| 月 / 周 / 日 | 东财 → 腾讯 `fqkline`（前复权）→ 新浪 |
| 60 / 30 / 15 分钟 | 东财 → 腾讯 `mkline` → 新浪 |
| 120 分钟 | 由 60 分钟合成 |
| 股票池 / 板块 / 个股资金流 | 东财 `push2delay`（延时主机，正常主机被拒时仍可用）|
| 咨询量 | 东财资讯检索 |

**东财排第一，恢复后无需改代码自动切回。** 每轮结束打印命中统计（`tencent 900次(50%) …`），
用来发现"东财悄悄恢复了"。

### 熔断器（可恢复）

没有熔断器时，一个挂掉的源会让整轮跑不完：每次请求 3 次重试 + 退避 ≈ 2~4 秒，
3.1 万次无效等待 ≈ 20 小时。

但**永久熔断也是错的**：被限流的源不等于死掉的源，缓一会儿就能用。

所以是半开状态：连续失败 8 次 → 熔断 → 冷却 90 秒 → 放一个探针 → 成功就完全恢复。
只统计**连续**失败，一次成功就清零，避免把偶发抖动误判成宕机。

### 需求 4 的历史：本地按日快照

需求要 A-3 / A-2 / A-1 / A 四个交易日，但**没有接口能稳定给到多日**：

| 接口 | 实测行为 |
|---|---|
| `push2his` 的 fflow | 能给 10 天，但**间歇性**，同一分钟内时通时断 |
| `push2delay` 的 fflow | 稳定，但不管 `lmt` 传多少都只给最新 1 天 |
| 个股资金流（分母） | 只有当日，无历史接口 |

改成本地累积：每个交易日运行时把当天的板块流入 + 全市场基准存进
`data/flow_history/YYYY-MM-DD.json`，历史自己攒。

**当外部依赖不可靠时，把状态挪到自己这边。** 某天接口抽风只丢那一天，
不会让整张表出不来。首次部署要跑满 4 个交易日才有完整的表。

# 使用说明

## 四张表的阅读顺序

从板块往下，不要从个股往上。从 5200 只 KDJ 开始筛会得到几百只金叉股，然后无从下手。

```
1. 04 板块热度    → 今天资金往哪去？选 2~3 个连续升温的方向
2. 02 放量TOP200  → 这些方向里谁在放量？（倍数 > 3 且 基准期CV < 0.6）
3. 03 升温TOP100  → 放量的这些，消息面跟上了吗？（先看基准期条数，< 5 跳过）
4. 01 KDJ全周期   → 候选股的月/周/日是否同向？
   → 缩到 10~20 只，写进 data/watchlist.txt
```

每一步都在减少候选数量，而且每一步的理由都说得清。

## 十个周期的分工

| 层级 | 周期 | 看什么 |
|---|---|---|
| 趋势层 | 上一月 / 本月 / 上一周 / 本周 | 大方向有没有变，仓位该多重 |
| 波段层 | 上一日 / 本日 | 这两天是在积累还是在消耗 |
| 择时层 | 120 / 60 / 30 / 15 分钟 | 今天什么时候动手 |

**共振指三层同向。** 单看择时层的 15 分钟金叉，一天能出几百个，没有筛选价值。

## 五个常见的读表错误

| 错误 | 为什么错 |
|---|---|
| J 值 -20 超卖了，抄底 | 下跌趋势里 J 值可以天天是负的。先看月/周方向 |
| 放量 10 倍，主力进场 | 放量也可能是出货，量本身没有方向 |
| 咨询量升温 8 倍，有大事 | 可能基准期只有 2 条，也可能是同名误命中 |
| 这个板块占比最高，最热 | 可能已经涨了三天。看 A-3→A 的**趋势**，不是今日**水平** |
| 15 分钟金叉了，进场 | 日内噪音，必须先过前三层 |

## 需求 4 读表陷阱：属性类板块会霸榜

概念板块里混着「融资融券」「沪股通」「百元股」「MSCI中国」这类**属性标签**，
覆盖大半个市场，占比必然排最前（实测融资融券 99.9%）。

你要的是「创新药 / 储能 / 光模块 / AI应用」这类**题材板块**，读表第一步就跳过属性类。

## 需求 3 的正确用法：watchlist 模式

全市场 5200 只逐个搜资讯约 2.2 万次请求，会被限流。默认跑沪深300。

**实践中最有用的是先筛后查**：

```bash
# 用需求 1/2/4 筛出候选，写进 data/watchlist.txt（每行 `代码,名称`）
python3 run.py --task 3 --sentiment-universe watchlist   # 十几只只要几秒
```

## Excel 操作要点

- 需求 1 是**两行合并表头**，开筛选要**选中第 2 行**（K值/D值/J值 那行），选第 1 行会失败
- 需求 4 选中四列占比 → 插入迷你图（折线），一眼看出哪些板块在持续升温
- 同一天的午盘批和收盘批是**两个文件不互相覆盖**，可以对比"半天"和"全天"

# 维护说明

## 参数在哪改

全部集中在 `radar/config.py`：

| 参数 | 默认 | 什么时候改 |
|---|---|---|
| `concurrency` | 12 | 经常超时/限流就调低到 6~8 |
| `qps_limit` | 30 | 同上 |
| `kline_limit` | 120 | 一般不动，改小会影响 KDJ 收敛 |
| `kdj_n / m1 / m2` | 9 / 3 / 3 | 通达信默认，改了要同步改文档和测试 |
| `cv_windows` | (20, 30) | 想看不同窗口的活跃度 |
| `sentiment_universe` | hs300 | 改成 watchlist 更实用 |
| `sector_type` | concept | 想看行业板块改成 industry |
| `disabled_providers` | 空 | 临时禁用某个源做对比验证，如 `{"tencent"}` |
| `provider_failure_threshold` | 8 | 熔断阈值 |
| `provider_cooldown_seconds` | 90 | 熔断后多久放探针 |
| `limit_symbols` | 0 | 调试用，或直接 `--limit 30` |

其他维护入口：

| 要改什么 | 改哪里 |
|---|---|
| 十个周期的定义和顺序 | `radar/config.py` 的 `TIMEFRAME_COLUMNS` |
| Excel 表头文字 | `radar/tasks/task*.py` 的 `HEADERS` |
| 定时时间 | `scripts/install_launchd.sh` 的 `make_plist` 调用 |
| 午盘批跑哪些任务 | `scripts/run_radar.sh` 的 `case` 分支 |
| 自选股清单 | `data/watchlist.txt` |
| 日志/报表保留天数 | `scripts/run_radar.sh` 末尾的 `-mtime` |

## 常用命令

```bash
python3 tests/test_indicators.py                    # 指标测试（11 个，不需要网络）
python3 run.py --task 1 --limit 30                  # 链路自检
python3 run.py --task all                           # 全市场
python3 run.py --task 4 --sector industry           # 行业板块而非概念板块
python3 run.py --task 3 --sentiment-universe watchlist
python3 -m radar.trading_calendar                   # 交易日判断
python3 run.py --clear-cache                        # 清缓存
./scripts/run_radar.sh close                        # 手动跑一次批次（和 launchd 同一条路径）
./scripts/install_launchd.sh install|status|uninstall
```

## 每日健康检查（30 秒）

```bash
ls -la data/output/ | grep $(date +%Y%m%d)
grep -E "扫描完成|数据源命中|完成，耗时" data/logs/run_$(date +%Y%m%d).log
```

| 指标 | 正常 | 异常 |
|---|---|---|
| 文件数（收盘批） | 4 个 | 少于 4 个 → 看日志哪个任务失败 |
| 失败数 | < 100 只 | > 500 只 → **当天数据不可用** |
| 耗时（全市场） | 15~25 分钟 | > 40 分钟 → 被限流，调低 concurrency |
| 数据源命中 | 单一源占比高是正常的 | 全部熔断 → 网络或接口全挂 |

**每次打开表，先看「口径说明」页的"抓取失败"数。** 这个习惯比任何指标都重要。

## 三层日志，从外往里查

| 层 | 文件 | 什么时候看 |
|---|---|---|
| launchd | `data/logs/launchd.*.err.log` | 脚本根本没起来 |
| 脚本 | `data/logs/radar_日期_批次.log` | 交易日判断、批次起止 |
| Python | `data/logs/run_日期.log` | 进度、失败明细、数据源命中 |

## 故障排查

**手动跑没问题，launchd 定时跑就失败** —— 最常见是 PATH。launchd 的环境变量和终端不一样。
看 `data/logs/launchd.close.err.log`，确认 plist 里的 `PATH` 包含 python3 所在目录。

**失败数突然从几十涨到几百** —— 先手工 curl 验证接口通不通：

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  'https://push2delay.eastmoney.com/api/qt/clist/get?pn=1&pz=2&po=1&np=1&fltt=2&invt=2&fid=f12&fs=m:1+t:2&fields=f12,f14'
```

200 = 接口正常，问题在本地；其他 = 接口或网络问题。**这一天的数据不要用。**

**本机走代理时全线失败** —— Python 默认读 `HTTP_PROXY` 环境变量，代理挂了就全挂：

```bash
RADAR_USE_PROXY=0 python3 run.py --task 1 --limit 10
```

**KDJ 和行情软件对不上** —— 按这个顺序查：

| 检查项 | 正确做法 |
|---|---|
| 复权方式 | 必须前复权。不复权时除权日会出巨大假死叉 |
| 平滑算法 | 递推 `K=(2K+RSV)/3`，**不是** `rolling(3).mean()` |
| 初值 | K、D 初值都是 50，不是 0 |
| 历史长度 | `kline_limit` 至少 120，太短则初值残影没衰减掉 |

差 0.01~0.05 正常，差 1 以上就有问题。

**「本日」的 KDJ 上午和下午不一样** —— 这是对的。「本日/本周/本月」指当前尚未走完的周期。

**Excel 打不开筛选** —— 需求 1 是两行合并表头，必须选中**第 2 行**再开筛选。

## 改代码的规矩

| 改什么 | 必须做什么 |
|---|---|
| 指标算法 | 先改 `docs/methodology.md`，再改代码，补测试，跑 `tests/test_indicators.py` |
| 任何代码 | 改完先 `--limit 30` 验证，不要直接跑全市场 |
| 口径 | 同步更新每个 xlsx 的「口径说明」sheet |

**11 个单元测试必须全绿才算改完。**

### 三条不能违反的数据原则

1. **数据不足时返回 `None`，不返回 0。** J 值填 0 会被读成"超卖"，这是会导致真实亏损的错误。
2. **不用更短的窗口凑数。** 样本从 30 降到 5，CV 的方差会大到没有意义，
   但表格里看起来"正常" —— 这种静默失真比缺数危险得多。
3. **口径必须写进产出物。** Excel 会被转发，文档不会跟着走。

# 已知边界

- **只做数据加工，不给投资建议，不接任何交易接口。** 这是项目边界，不是技术限制。
- KDJ、成交量 CV、资金流都是**对已发生事实的统计描述**，不包含未来信息。
- 「咨询量」是市场注意力的**代理变量**，存在同名误命中和翻页截断，横向比较优于绝对值。
- 数据源为第三方公开行情接口，**没有官方文档也没有服务承诺**，字段可能改名、接口可能下线。
- 需求 4 的板块占比之和 **≠ 100%**（概念板块互相重叠，实测约 1700%）。
- 北交所默认剔除（需求只要深沪两市）。
- 不要把请求频率调到远超正常使用 —— 既是稳定性问题，也是分寸问题。
